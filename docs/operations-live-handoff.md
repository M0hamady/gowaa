# Jowwa Operations — Live Handoff

## الحالة الحالية

- الفرع الحالي: `feat/operations-test-workspace`.
- الحالة: Release Candidate للاختبار، وليس اعتماد إنتاج.
- آخر تحقق: `npm test` — 300 اختبار ناجح، 0 فاشل.
- رحلة Browser QA المحلية: عميل، رابط المحل والاستلام، عامل الصالة، المطبخ، الكاشير، التحصيل، التسليم وإخلاء الطاولة.
- كل بيانات التشغيل الحالية تجريبية ومحلية، ولا تمثل حسابات أو طلبات حقيقية.

## دليل العزل

- نسخة الاختبار تستخدم `public/operations-build.json` بعلامة `liveBackend=false`.
- الدفع والرسائل والهوية الحقيقية مقفولة في نسخة الاختبار.
- `vercel.json` حاليًا يستخدم `scripts/build-ops-test.mjs`، وهو build خاص بالاختبار ويمنع production.
- لا يجوز ترقية هذا الفرع أو هذا الـbuild إلى production alias.

## ما تم اعتماده داخل الاختبار

- الأدوار وصلاحياتها منفصلة.
- المطعم، السوبر ماركت، مقدم الخدمة المنزلي، التوصيل، الطاولات، الكاشير، المطبخ، المخزون والوصفات لها حدود اختبارية.
- الطلبات والتحصيل والمخزون والتوصيل لها اختبارات idempotency وقيود صلاحيات.
- رابط المحل يفتح الكتالوج ويجعل الاستلام من المحل هو الاختيار الافتراضي.
- عامل الصالة يفتح حساب طاولة ويضيف أصنافًا ويرسلها للمطبخ.

## متطلبات فتح الإنتاج — لم تُنفذ بعد

1. إنشاء production build منفصل لا يستورد fixture store ولا يعرّض تبديل الأدوار.
2. ربط التشغيل بخادم مصادق عليه وقاعدة production/staging منفصلة مع RLS ومراجعة migrations.
3. تعريف حسابات حقيقية وصلاحيات server-side بدل بيانات `fixtures.mjs`.
4. تفعيل بيئة دفع sandbox أولًا مع callback وwebhook idempotency؛ لا يُستخدم live payment قبل اعتماد مالي منفصل.
5. إعداد SMS/auth، أسرار الإنتاج، حدود المعدل، سجلات التدقيق والتنبيهات.
6. مراجعة الخصوصية للعنوان، الموقع، بيانات العميل، التتبع، والاحتفاظ بالسجلات.
7. تنفيذ Browser QA على staging متعدد الأجهزة، ثم smoke test production read-only بعد النشر.
8. تجهيز rollback، backup متسق، مراقبة الأخطاء، وخطة إيقاف فورية.

## قرار النشر

القرار الحالي: **ممنوع النشر إلى اللايف** حتى يتم تنفيذ المتطلبات السابقة ومراجعتها. الموجود جاهز للتسليم كنسخة اختبار موثقة، وليس كاتصال إنتاج.
